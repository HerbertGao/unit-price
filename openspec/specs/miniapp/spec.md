# miniapp 规范

## 目的

`apps/miniapp`（`@unit-price/miniapp`）是浏览优先的 Taro 微信小程序：读取一份榜单快照后在端上本地派生软饮榜、分类下钻、搜索和分页，通过无状态 `/compute` 提供结构化即时比价，并以受 Taro 支持的 React 运行时稳定加载。浏览路径不解析脏标题、不重算单价、不贡献或纠错入库。

## 需求

### 需求:miniapp 必须是消费 /rankings 的只读榜单小程序骨架

`/rankings` 改为全量快照后,端上消费口径随之改形:榜单/搜索/下钻榜数据**必须**通过 `@unit-price/api-client` 的 `buildRankingsUrl` + **`parseRankingsSnapshot`** 消费 `GET /rankings`(单参、`jitless` 已内置),`parseRankingsResponse` 随旧数组形状一并消失。即时比价仍走 `buildComputeUrl` + `parseComputeResponse`。网络层仍用 `Taro.request`。

**只读边界不变**:禁止扫码 / 拍照 / 贡献 / 纠错 / 写库入口;端上不跑 tier1 解析或单价计算。唯一的写形请求仍是 `POST /compute`。

**请求次数改变**:一次页面挂载取一份快照,cohort 切换 / 翻页 / 搜索**不再发任何请求**——它们是同一份对象上的本地派生。`分类` Tab 仍只读消费 `GET /categories`;其下钻榜**不再**发起 `GET /rankings?category=<slug>`。

#### 场景:浏览只读、即时比价不在端上计算

- **当** 检查端上代码路径
- **那么** 不得出现扫码 / 拍照 / 贡献 / 纠错 / 写库入口;不得在端上跑 tier1 解析或单价计算
- **那么** 派生视图(cohort 过滤 / 搜索 / 切片)是纯本地操作,**不构成**端上计算单价——它们不产生任何新的 `per100ml`

#### 场景:三个底部 Tab 且边界不变

- **当** 检查底部 Tab
- **那么** 仍为 `榜单` / `分类` / `我的` 三个,各自边界不变

#### 场景:经 api-client 消费 /rankings

- **当** 端上取榜单数据
- **那么** 必须用 `buildRankingsUrl` 构造 URL、`Taro.request` 发请求、`parseRankingsSnapshot` 校验响应;**禁止**手写重复的响应类型或绕过校验
- **那么** `parseRankingsResponse` 不得再被引用——它已随旧数组形状移除

#### 场景:miniapp 不进根 tsc -b reference 图

- **当** 跑根 `tsc -b`
- **那么** miniapp 不在 reference 图内,其类型检查由自身构建承担

### 需求:榜单一屏必须支持分页与加载/空/错三态

分页**必须**支持:**下拉刷新**(重取快照并重置到第一屏)+ **触底加载**(揭示下一段本地切片,直到切片耗尽即到底)。分页是**本地切片**,不发请求。

三态**必须**明确:**loading**(首次加载有指示)、**空**(无入榜项时显示空态而非空白或报错)、**错误**。

**两个错误位收敛为一个**:原「首屏错 vs 翻页错」的区分建立在「翻页是一次网络请求、会失败」之上。本地切片不会失败,故**翻页错不再存在**,一并删除其局部重试入口——一个永不可达的重试按钮不是防护网,它只是读起来像。剩下的唯一错误位是**首屏错**(快照 fetch 或其校验失败且屏上无数据 → 整屏错误态 + 重试入口)。任一错误态**禁止**白屏或渲染脏数据。

**落地 cohort 是具名常量 `LANDING_COHORT`,不是推导结果**。调用方未指定 cohort 时用它。**禁止**改为「从树上推导最浅的单一可比轴节点」——该规则无唯一解(`soft-drink` 与 `dairy` 同为 root 直子且同为 `per_100ml`),实测会落到乳品榜。它**必须与榜标题文案(`SCOPE_TEXT`)指同一 cohort**:标题本就是常量,只推导 slug 才是两者能对不上的原因;二者不一致时用户会在写着 A 的标题下看到 B 的榜。**唯独** taxonomy 未播种(树为空)时该常量不在树中,那是合法退化态、走空态,不得判为未知品类。

**空态必须区分「暂无数据」与「该 cohort 无法开榜」**:目标节点跨多个可比口径、或 slug 不在树中时,派生被拒绝。此时**禁止**沿用「下拉刷新试试」文案——下拉永远不会让它有数据。**唯独** taxonomy 未播种(树为空)是合法退化态,按普通空态呈现,不得报成「该分类不存在」。

**触底揭示不得被后台重验打断**:命中缓存后的后台重验成功时**禁止**重置已揭示的切片长度,否则用户正在滚动的列表会在手指下弹回第一屏。下拉刷新与首屏重试**必须**重置。

#### 场景:升序榜单与字段渲染

- **当** 渲染榜单行
- **那么** 按 `per100ml` 升序呈现,序取自服务端下发、端上不重排;字段渲染口径不变

#### 场景:下拉刷新与触底分页

- **当** 用户下拉刷新
- **那么** **必须**重取快照、重置到第一屏切片
- **当** 用户触底
- **那么** **必须**揭示下一段本地切片、**不得**发起请求;切片耗尽即到底
- **当** 命中缓存后的后台重验成功返回
- **那么** **禁止**重置已揭示的切片长度

#### 场景:加载/空/错三态（首屏错与翻页错分开）

- **当** 首次进入加载期间
- **那么** **必须**有 loading 指示
- **当** 快照为空或派生视图无行
- **那么** **必须**显示空态,不得空白或报错
- **当** 首次加载 `/rankings` 失败或 `parseRankingsSnapshot` 抛错且屏上无数据
- **那么** **必须**整屏错误态 + 重试入口
- **当** 用户触底翻页
- **那么** **不存在**翻页错误位:本地切片不会失败,故**禁止**保留翻页错误态与其局部重试入口
- **当** 目标 cohort 跨多个可比口径,或其 slug 不在树中
- **那么** **必须**呈现与「暂无数据」可区分的说明,**禁止**提示下拉刷新
- **当** taxonomy 未播种(树为空)
- **那么** 按普通空态呈现,**不得**报成「该分类不存在」

### 需求:列表内必须预留降级版原生广告位（v1 不接真实广告）

榜单**必须**预留一个**列表内原生广告位组件**。**插入位置确定化**（避免约数不可测）：前 10 条（渲染序号 ≤ 10）之间**禁止**任何广告位；自第 10 条之后**每 12 条**设一个广告位插入点（插入点在渲染序号 10、22、34… 之后）。v1 该组件**必须**为「降级占位」：**禁止**接入真实广告单元、**禁止**依赖流量主开通（流量主硬门槛累计 UV ≥ 1000，v1 上线无法服务）。

**填充态与卡高分清（消除「固定卡高」与「无填充塌缩」的表面矛盾）**：广告位**有填充**（未来接入真单元、有广告返回）时**才**占用预留固定卡高；**无填充**时**必须渲染为零高度空内容**（`height===0`、无可见占位卡框、列表不跳版）。说明「无可见占位」≠「无宿主节点」：第 10 条之后的插入点**可保留一个零高度的 wrapper 宿主节点**（供未来填充挂载），其子树在 v1 为空故 `height===0`、视觉上不占空间；而前 10 条区段**根本不设插入点**（真·无广告位 DOM）。v1 恒无填充（未接真单元），故该组件 v1 **实际恒不显示任何可见内容**——占位/插入逻辑就位、待未来接单元即生效。**禁止**使用插屏广告（高频工具强制弹窗）；激励视频留到有奖励钩子时（非本期）。

#### 场景:前 10 条无广告、之后每 12 条一个插入点

- **当** 用户浏览榜单前 10 条（渲染序号 ≤ 10）
- **那么** 这 10 条之间**禁止**出现任何广告位插入点；广告位插入点**必须**只在第 10 条之后、每 12 条一个（序号 10、22、34… 后）

#### 场景:v1 降级位恒无填充、渲染为空

- **当** v1（未接真实广告单元）下广告位无填充
- **那么** 该广告位**必须**渲染为零高度空内容（`height===0`、无可见占位卡框、列表不跳版）；固定卡高**仅**在未来有填充/加载真广告时才占用——v1 恒无填充故**恒不占空间**。可断言两点：① 前 10 条区段**零广告位 DOM**（无插入点）；② 第 10 条之后首个插入点 wrapper（须渲染 ≥11 行使其挂载）在 v1 实测 `height===0`（区分 v1 无填充态 vs 未来有填充占卡高）

#### 场景:不用插屏

- **当** 检查 miniapp 的广告形态
- **那么** **禁止**使用插屏（interstitial）广告；v1 仅列表内原生降级位

### 需求:榜单首页必须遵循共享视觉 tokens

榜单首页(榜单 Tab)**必须**遵循 [`apps/miniapp/DESIGN.md`](../../../apps/miniapp/DESIGN.md) 的视觉规则。设计 tokens(色板、字阶、间距、圆角、阴影)**必须**集中落地于 `app.css`;**禁止**在页面 / 组件的 css 或内联 style 散写色板字面量,页面 / 组件只能引用 CSS 变量(`var(--…)`);复用的榜单行与加载/空/错状态必须由共享组件承载(原生 `tabBar` 的配置与 PNG 图标不在 React 组件约束内)。

榜单首页**必须**至少呈现品牌头(`会员商店值不值`)、顶部搜索入口、静态范围说明条和榜单列表(每行含 rank 徽标、`per100ml` 大字、整件价)。范围说明条只声明端上从全量快照本地派生出的软饮 cohort 与单位口径(如「山姆软饮真实单价榜 · 元/100ml」)。服务端没有快照级件数或统一更新时间,因此该条**禁止**声称动态件数 N 或「更新于 X月X日」;逐行 `capturedAt` 仅用于行级新鲜度。

#### 场景:首页视觉元素齐全
- **当** 进入榜单 Tab
- **那么** **必须**可见:品牌头 `会员商店值不值`、顶部搜索入口、**静态范围说明条**、以及榜单列表(每行含 rank 徽标 / `per100ml` 大字 / 整件价);范围说明条**禁止**出现动态件数 N 或采集日期

#### 场景:设计 tokens 集中(机械可验:页面 css 零颜色字面量)
- **当** 对 `apps/miniapp/src` 的 **`pages/**` 与 `components/**` 下的 `.css` 与组件 JSX 内联 `style`**(**不扫 `app.css` 自身**——它是 token 定义处、允许出现色值)`grep` 任意颜色字面量(`#` 3/6/8 位 hex、`rgb()` / `rgba()`、`hsl()` / `hsla()`、具象命名色)
- **那么** 页面 / 组件的 css 与内联 style **禁止出现任何**颜色字面量(hex / rgb(a) / hsl(a) / 具象命名色;**不含** `transparent` / `inherit` / `currentColor` 等功能性关键字)——一律改用 `var(--…)`(含**阴影走 `var(--shadow)`**,不得直写 `rgba(...)`);颜色字面量**只允许**出现在 `app.css` 的 token 定义处(既有 `index.css` 的旧硬编码色**必须**已清理为变量引用)。**例外(不在本 grep 范围)**:`app.config.ts` 与各页 `*.config.ts` 的原生配置色字段(`window.navigationBarBackgroundColor`、`tabBar` 的 `color` / `selectedColor` / `backgroundColor`)、以及 tabBar PNG 图标——小程序框架限制、不能引 CSS 变量,故豁免;其中 tabBar **`selectedColor`(及选中图标烧入色)必须 = `--blue`(`#014B90`)**,其余原生配色字段按 DESIGN.md 取**对应** token 同值(如导航栏背景取 `--paper` 同值、tabBar 未选中 `color` 取 `--muted` 同值、tabBar `backgroundColor` 取 `--paper-card` 同值),**不强制全部 = 蓝**

#### 场景:可比单价仍以 per100ml 呈现、不被整件价反推
- **当** 渲染榜单行
- **那么** 行内**必须**以服务端 `per100ml` 作为可比真值的大字呈现,整件价(`priceCents / 100`)仅作参考标价;**禁止**用整件价反推或替代 `per100ml`

### 需求:搜索入口为真输入、跳转复用 board 列表页

顶部搜索入口**必须**仍为**真输入**:用户输入商品名后跳转复用 board 列表页。**但搜索不再发起请求**——它是当前 cohort 内对已持有快照的本地子串筛选,口径由 `api-client` 单方定义(`trim` → **有效码点数 < 2 则匹配空集** → 按码点截断 ≤64 → 仅 `A-Z`↔`a-z` 折叠 → 子串),端上**禁止**另写一份匹配规则。

**搜索的 cohort 必须显式**:落地页的搜索继承 `LANDING_COHORT`(定义见「榜单一屏必须支持分页与加载/空/错三态」需求),不得在无 cohort 的情况下搜索——那会退化成对某个任意 cohort 的搜索。深链或手输的 `board?q=…` 若未带 cohort,同样按 `LANDING_COHORT` 处理,不得渲染无 cohort 的结果。

搜索**仍不构成**贡献 / 纠错路径。

#### 场景:输入商品名后跳转复用 board 列表页搜索

- **当** 用户在搜索框确认输入
- **那么** 跳转 board 列表页并带上搜索词与所属 cohort;**不得**发起网络请求

#### 场景:board 标题按来源派生

- **当** board 页由搜索进入
- **那么** 标题按搜索词派生;由分类下钻进入时按品类派生

#### 场景:含 % / & 的搜索词逐字节往返不变

- **当** 搜索词含 `%` / `&` / `_` / `!`
- **那么** 按字面量匹配,不做通配解释;因不再有 URL 往返,原「逐字节往返不变」由「本地匹配不改写词」承载

#### 场景:空输入或单字不发起请求

- **当** 输入为空或有效码点数 < 2
- **那么** 不进入搜索态。原「不发起请求」在快照形态下恒成立,该门的作用改为**防止单字命中几乎整个 cohort**
- **当** 这样的词仍经深链或手输抵达列表页(入口拦不住它)
- **那么** 必须**匹配空集**,不得落回「不过滤」而端出整个 cohort——页面标题此时写着「搜索:X」,端出全量等于宣称每一行都命中了该词

### 需求:分类 Tab 必须以只读品类树呈现并可下钻到 category-scoped 榜

`分类` Tab 仍**仅**发起只读 `GET /categories` 呈现整树。其下钻的 category-scoped 榜**不再**发起 `GET /rankings?category=<slug>`,改为在同一份快照上按该节点本地过滤。

可点性判据不变:必须只用 `node.rankable`;节点契约中不再存在 `rankableCount`。

若界面将来需要展示某节点的实际榜行数,必须从当前持有的同一份快照按该节点派生后计数,不得请求或重建服务端节点计数。当前分类树不展示数量徽标。

#### 场景:经 api-client 只读消费 /categories

- **当** 分类 Tab 取树
- **那么** 必须用 api-client 的 categories 契约,只读、不写库

#### 场景:可点性由 rankable 闸口

- **当** 判定某节点是否可点进
- **那么** 必须只用 `node.rankable`;categories 与快照节点 schema 均不得暴露 `rankableCount`

#### 场景:节点数量只从同一快照派生

- **当** 界面需要展示某节点的实际榜行数
- **那么** 必须从当前快照按该节点派生并计数,不得使用独立服务端计数字段

#### 场景:下钻 category-scoped 榜

- **当** 用户点进一个 `rankable=true` 节点
- **那么** 该榜必须由端上在快照上按该节点过滤得出,**不得**发起 `GET /rankings?category=<slug>`
- **那么** 归属判据是「行的任一 `categorySlugs` 是该节点或其后代」,对叶与非叶一致

#### 场景:未播种 taxonomy 的空态

- **当** taxonomy 未播种
- **那么** 分类树与快照同为空,呈现空态、不报错

### 需求:榜单首页必须提供即时比价入口并承载结构化比价表单页

`榜单` 首页**必须**提供进入**即时比价**的入口,服务「在店遇到未收录商品、想当场知道它单价贵不贵 / 排哪」的场景。入口采用**搜索未命中为主、紧凑常驻为辅**两处,**禁止**在首页放抢占浏览视线的大块主 CTA:

- **主入口——搜索无结果态**:当商品名搜索返回**零结果**时,空态**必须**呈现比价 CTA(如「没搜到这件商品？」+ 按钮「输入规格,算它值不值」)→ 进入比价表单页。这是主路径,贴合「这件没收录」的真实触发点。
- **辅入口——搜索框旁紧凑常驻**:首页搜索行旁**必须**有一个**视觉次于搜索**的紧凑入口(文本链接 / 图标按钮,如「算单价」,**非**整行大按钮)→ 进入比价表单页,覆盖「搜索前就知道没收录」的用户。

**比价表单页**字段**必须**含:总价(元)、数量、**单件容量 或 总容量(二选一互斥)**、单位选择(`ml`/`L`/`g`/`kg`)、品类选择。品类选择**必须**从 `/categories` 树(或共享 `CategoryLeafSlugSchema`)派生 leaf cohort 列表,**禁止**在 miniapp 内硬编码品类清单(防漂移)。提交**必须**经 `@unit-price/api-client` 的 `buildComputeUrl` + `parseComputeResponse` 调**无状态** `POST /compute`,渲染结果卡片:用户单价(`per100ml`/`per100g`)+ 可展开的可回放 `formula` + 在该 cohort 的 `rank`/`total`/`percentile` + 最接近的若干同类品(可点进 board)。端上**必须**做轻量 UX 校验(总价/数量/容量为正、二选一互斥、按所选品类的可比单位轴约束可选单位)以**减少空跑**,但**权威校验在服务端**(信任边界);**空 / 非法输入禁止发起请求**。

### 需求:榜单首屏必须经端上 SWR 缓存即时回显并后台重验

**缓存范围与键**:缓存**整份快照**,键为**单一固定字面量**(不再按 cohort 分键)。cohort / 搜索 / 翻页都是同一份对象上的本地派生,分键会缓存同一份数据的多个副本。原「搜索与翻页禁止缓存」的规则随之消失——它防的是「缓存了一个过滤后的子集却当全量用」,而现在缓存的就是全量。

**换键而非兼容旧值**:旧键存的是 `RankingsItem[]`(数组),过不了新的对象 schema。换用新键保证正确性;清理旧键**仅**为回收端上存储配额,不是正确性手段。

**读即重校验**:读缓存**必须**经 `parseRankingsSnapshot(raw)` 重新校验(单参);损坏 / 旧 schema 残留 → **必须**视作未命中,**禁止**渲染未校验脏数据。

**无 TTL 是已知接受项**:缓存不带生成时刻,故命中时呈现的可能是任意旧的快照,直到后台重验回来覆盖。SWR 的即时回显是它的对价。

#### 场景:命中缓存即时回显 + 后台刷新覆盖

- **当** 端上存有可通过校验的快照
- **那么** **必须**立即回显、不进整屏 loading,并在后台重取覆盖

#### 场景:命中后触底翻页不重复首页

- **当** 命中缓存后用户触底
- **那么** 揭示下一段本地切片;因整份快照已在手,**不存在**「重复请求首页」的可能
- **那么** 后台重验成功时**禁止**把已揭示长度重置回第一屏

#### 场景:有缓存时后台重验失败保留旧数据

- **当** 命中缓存后后台 fetch 或 `parseRankingsSnapshot` 校验失败
- **那么** **必须**保留已回显的旧数据,不得回退整屏错误态

#### 场景:缓存缺失回落既有三态

- **当** 无缓存或缓存校验失败
- **那么** 回落 loading → ready / 空 / 首屏错三态

#### 场景:仅缓存非搜索首页

- **当** 检查写缓存的时机
- **那么** 写入的**必须**是整份快照本身,与当前 cohort / 搜索词 / 已揭示长度无关;**禁止**缓存任何派生后的子集

### 需求:榜单行必须按失效置灰并在现价高于历史低价时标注历史低价

榜单行组件(`RankingRow`)**必须**消费 `/rankings` 响应的 `capturedAt` 与 `lowestPriceCents`,做两项**逐行**读侧标注(纯前端派生,不改榜单请求/排序/分页):

- **失效置灰**:当 `now - capturedAt > STALE_AFTER_MS` 时,该行**必须**呈现为「失效/灰态」视觉(整行降饱和/置灰),以示该单价久未更新;但该行**仍在榜内**(失效**不下架**,它正是「历史上便宜」的参考项)。置灰**仅为视觉**、以客户端当前时间判定;**禁止**依赖服务端返回的失效布尔。阈值 `STALE_AFTER_MS = 30*24*60*60*1000` 由**小程序侧具名常量**提供(前端**禁止**另写魔法数字):**不从 `@unit-price/core` import**——小程序对 core 无依赖边(仅依赖 `@unit-price/api-client`、经 esbuild vendor 别名绕开 babel 对 Zod 的 class-transform),新开 miniapp→core 边既是幽灵依赖、又重入该 Zod 捆绑坑;`STALE_AFTER_MS` 是裸数字、定义在小程序侧最简且零捆绑风险。
- **历史低价标注**:仅当 `priceCents > lowestPriceCents`(现价高于历史低点)时,该行**必须**呈现「历史低 ¥X.XX」标注(`lowestPriceCents/100` 两位小数);`priceCents <= lowestPriceCents`(现价即历史低点)时**禁止**呈现该标注(无「错过抄底」信号,免噪)。
- **缺字段降级(跨版本 / 旧缓存)**:`capturedAt`/`lowestPriceCents` 契约为 `.optional()`,故旧服务端或 CDN 24h 旧缓存响应可能缺其一。缺 `capturedAt` 时**禁止**置灰(`now - undefined` 判定为非失效),缺 `lowestPriceCents` 时**禁止**呈现历史低价标注——即退化为无标注的既有行为,**禁止**崩溃或整屏错。
- 置灰与历史低价标注**相互正交**:一行可同时失效且现价高于历史低点,两标注可并存。
- **三价并存是可接受的呈现结果**:一行可同时展示 `per100ml`(排序大字)、`priceCents`(最新整件价)、`lowestPriceCents`(历史低)三个口径不同的价。徽标只对比 `priceCents` vs `lowestPriceCents`(同为整件分)、**不与 `per100ml` 混算**。`per100ml` 与 `priceCents` **同源于最近一次成功解析**(重报命中去重时派生值随之刷新,见 `persistence`/`rankings-api`),但仍有四类窗口可不同源、且并非都会自动自愈(见 `rankings-api`「口径漂移」;其中解析失败要靠再重报一次收敛,解析漂移遗留的旧行**不可修**、属已披露残留);UI 是否把「历史低」徽标与排序大字在视觉上分离由本需求交实现斟酌。**客户端禁止**据此做任何一致性校验或把不一致呈现为错误——三口径本就分母不同。
- **标注随 `RankingRow` 组件生效于其所有渲染面**:`RankingRow` 除榜单列表外,还被即时比价页复用渲染 `neighbors`(邻居行)。邻居行是真实榜单行、带真实 `capturedAt`/`lowestPriceCents`(经 `projectNeighbor` 填充),故**同样**按上述规则置灰 / 标历史低——这是正确且期望的。但用户**自填的比价行**(非 `RankingsItem`、无 `capturedAt`/`lowestPriceCents`)**禁止**置灰或标注(走缺字段降级路径)。
- 本需求约束逐行标注的呈现逻辑,**不**引入榜单顶部「全局新鲜度横幅 / 更新于 X月X日」——该全局横幅尚未实现,与逐行置灰是独立能力。呈现所用颜色**必须**沿用 `app.css` 设计 tokens、**禁止**在页面/组件散写颜色字面量(遵既有「设计 tokens 集中」约束)。

#### 场景:>30 天未重报的行置灰但仍在榜
- **当** 榜单某行 `capturedAt` 距当前已超过 `STALE_AFTER_MS`(30 天)
- **那么** 该行**必须**呈现失效/灰态视觉,且**仍出现在榜单列表内**(未被移除、rank 序不因失效改变)

#### 场景:30 天内的行正常呈现
- **当** 榜单某行 `capturedAt` 距当前在 30 天以内
- **那么** 该行**必须**以正常(非灰)态呈现

#### 场景:现价高于历史低点时标注历史低价
- **当** 榜单某行 `priceCents = 1490`、`lowestPriceCents = 990`
- **那么** 该行**必须**呈现「历史低 ¥9.90」标注

#### 场景:现价即历史低点时不标注
- **当** 榜单某行 `priceCents = 990`、`lowestPriceCents = 990`(现价即历史低点)
- **那么** 该行**禁止**呈现历史低价标注

#### 场景:失效与历史低价标注可并存
- **当** 某行既 `capturedAt` 超 30 天、又 `priceCents > lowestPriceCents`
- **那么** 该行**必须**同时呈现灰态与「历史低 ¥X.XX」标注(两标注正交、不互斥)

#### 场景:缺字段的旧响应降级为无标注而非报错
- **当** 榜单某行(来自旧服务端 / CDN 旧缓存)`capturedAt` 或 `lowestPriceCents` 为 `undefined`
- **那么** 该行**禁止**置灰(缺 `capturedAt`)、**禁止**呈现历史低价标注(缺 `lowestPriceCents`),退化为无标注的正常行,**禁止**崩溃或触发整屏错

#### 场景:即时比价页的邻居行同样标注、用户自填行不标注
- **当** 即时比价页经 `RankingRow` 渲染 `neighbors`(一条失效且现价高于历史低点的邻居)与用户自填比价行
- **那么** 邻居行**必须**按规则置灰 + 标「历史低」(它是真实榜单行);用户自填行(无 `capturedAt`/`lowestPriceCents`)**禁止**置灰或标注

### 需求:miniapp 构建必须使用 Taro 支持的 React 运行时

`apps/miniapp` 的 React 运行时必须满足所安装 `@tarojs/react` 声明的 peer 主版本,且 `react-dom` 必须与 React 使用相同版本。开发与生产微信包在进入 webpack/Taro 编译前必须执行同一兼容检查;不兼容时必须以非零退出并报告实际版本与支持范围,不得产出一个“编译成功但 app.js 启动崩溃”的包。

#### 场景:兼容版本通过构建并注册首页

- **当** React 满足 Taro peer 范围且 react-dom 与其同版本
- **那么** miniapp test、TypeScript typecheck 与 weapp bundle 必须通过
- **那么** 微信开发者工具加载 app.js 时不得出现 `ReactCurrentBatchConfig` 读取异常,应用与 `pages/index/index` 必须完成注册

#### 场景:不兼容 React 主版本在打包前失败

- **当** 已安装 React 主版本不满足 `@tarojs/react` 声明的 peer 主版本
- **那么** `build:weapp` 与 `dev:weapp` 必须在进入 webpack/Taro 编译前非零退出
- **那么** 错误信息必须同时指出 React 实际版本和 Taro 支持范围

#### 场景:Dependabot 不发起超出 Taro peer 的 React major

- **当** Dependabot 检查 `react` / `react-dom` / `@types/react` 更新
- **那么** 必须忽略 semver-major 更新,不得创建 React 19 PR
- **那么** React 18 范围内允许的 minor/patch 更新仍可正常提出

#### 场景:React 与 react-dom 版本漂移在打包前失败

- **当** `react` 与 `react-dom` 的实际安装版本不一致
- **那么** 兼容检查必须非零退出并指出两者版本,不得继续生成微信包
