## Context

`GET /rankings` 把排序、分页、品类过滤、搜索都做在服务端,每个参数组合是一个独立的 CDN 缓存键(`Cache-Control: public, max-age=86400`)。有效品类 15 个,再乘分页与搜索词,键是发散的。

榜单全量当前 **389 行**。`/categories` 已经把整棵树(含 `parentSlug`、`comparableUnit`、`rankableCount`)一次性下发给客户端,而榜单行**没有**携带自己的叶品类 slug —— 这是客户端目前无法本地过滤的唯一缺口。

排序键 `per100ml` 是已落库的数值,服务端的 `ORDER BY` 与客户端的一次 sort 对同一数值集产出相同序列。**本变更不改变任何数字的来源**,只改变「谁来排」。

## Goals / Non-Goals

**Goals:**
- 榜单相关的 CDN 缓存键从 15+ 收敛为 **1**,让「刷缓存」从逐键动作变成单次动作。
- 品类切换、翻页、搜索变成**零网络**的本地操作。
- 用户在不同品类间看到的是**同一时刻**的快照(当前是各键各自过期)。

**Non-Goals:**
- 不做端上单价计算(`per100ml` 仍是存储值,端上只排序不重算)。
- 不删不改 `GET /rankings`。
- 不实现规模超限后的降级(只定义阈值与路径)。

## Decisions

### D1:新增快照端点,不改造 `/rankings`

`/rankings` 是已发布的公开只读 API,服务小程序之外的客户端与深链。把它改成「不分页返回全量」是破坏性变更,把它保留、另开一个全量端点则互不影响,且两者可共用同一投影逻辑。

**否决的替代方案**:
- **给 `/rankings` 加一个「返回全部」的参数** —— 同一个端点同时承担「分页视图」与「全量快照」两种缓存语义,两者的 TTL 与 purge 需求不同,混在一个键空间里正是本变更要消灭的问题。
- **直接把 `limit` 上限提到覆盖全表** —— 键仍随 `category`/`offset`/`q` 发散,一个缓存键都没省掉。

### D2:行必须携带叶品类 slug,祖先归属由客户端沿树推导

快照每行**必须**带其所属**叶**品类 slug。客户端已有 `/categories` 的全树(`parentSlug`),据此可自行判定「这一行是否属于某个祖先节点」,不需要服务端下发闭包。

**否决的替代方案**:
- **下发闭包表**(每行携带全部祖先 slug 数组)—— 冗余、payload 变大,而客户端已经有树了。
- **每行带完整路径字符串** —— 同样冗余,且路径格式会成为新的隐式契约。

### D3:cohort 守卫用 `/categories` 已有的 `comparableUnit`

跨 cohort 的节点(如 root `beverage`、`alcohol`)在 `/categories` 里 `comparableUnit` 为 `null`,这**已经是**契约字段。客户端据此直接拒绝,不必发一次注定 `400` 的请求。

服务端的 `resolveComparableUnitStatic` **不搬、不动** —— `/rankings` 与 `/compute` 仍用它守自己的边界;客户端的本地判定是**同口径的前置拦截**,不是替代权威。二者口径一致由「`comparableUnit` 由服务端解析后下发」结构性保证。

### D4:`rank` 由客户端在排序后赋值

现契约里 `rank = offset + 1-based index`,是**读时投影**、不是存储值。客户端排序后同样赋值,语义不变。快照端点的行**不携带** `rank`(在全量快照里它没有意义——`rank` 只在某个过滤+排序视图下才有定义)。

### D5:规模上限与失效阈值

本设计的成立前提是「整张榜能一次下发」。当前 389 行 ≈ 110KB 原始 / ~25KB gzip。

**明确的失效路径**:行数增长到快照体积影响首屏时,本设计失效,届时应回退到服务端分页(即今天的 `/rankings`,它**没有被删**,正是为此保留)。**本期不实现自动降级** —— 过早为一个尚未发生的规模写切换逻辑,会引入一条长期不被执行、因而必然腐坏的分支。

**但必须留下观测**:快照端点应在响应或日志中暴露行数,使「什么时候该重新评估」有据可依,而不是等用户抱怨首屏慢。

### D6:SWR 缓存从「每 cohort 一份」改为「一份快照」

既有需求是每个 cohort 一份端上缓存快照。改为单份后,冷启动只需读一份、重验只需一次请求,且不再有「不同品类缓存于不同时刻」的不一致。既有 SWR 的**行为语义**(先渲染缓存、后台重验、失败保留旧数据)**不变**,变的只是缓存对象的粒度。

## Risks / Trade-offs

- **[快照随目录增长变大]** → 见 D5:阈值明确、降级路径明确(回退 `/rankings`),并留行数观测。**这是本设计最主要的风险**,不是可以忽略的。
- **[首屏从「20 行」变成「全量」]** → 首次加载 payload 变大(~25KB gzip),但换来后续所有品类切换/翻页零网络。需实测首屏时间,**若首屏明显变慢则本设计的收益不成立**,应在验收时诚实比对而不是只报告缓存键数量。
- **[端上排序与服务端排序不一致]** → 同一数值集的升序排序在两侧应当相同,但**浮点相等值的次序**(`per100ml` 相同的两行)在不同实现下可能不同。须定义确定性的 tie-breaker(如按 `storeSku` 次级排序)并两侧一致,否则同一份数据在小程序与 web 上会呈现不同顺序。
- **[miniapp 五条需求同时改动]** → 变更面大,回归风险集中在榜单主路径。验收**必须**覆盖:榜单首屏、翻页、品类下钻、搜索、冷启动 SWR 五条路径,缺一不可。
- **[快照与 `/rankings` 两条投影漂移]** → 二者应共用同一投影逻辑;若各写一份,同一行在两个端点可能字段不一致。实现时必须共用,不得复制。

## Open Questions

- 快照端点的 `Cache-Control` 取值:沿用 `max-age=86400`,还是因为「只有一个键、purge 成本低」而取更长?取决于数据更新频率,可在实现时定。
- 搜索的本地实现口径:服务端 `q` 是子串匹配,本地须**同口径**(含大小写与全角/半角处理),否则同一个词在深链(走 `/rankings?q=`)与端上搜索结果不同。
