## Why

榜单目前把「排序 + 分页 + 按品类过滤 + 搜索」全放在服务端,于是**每一个品类、每一页、每一个搜索词都是一个独立的 CDN 缓存键**。实测品类 slug 有 17 个(其中 `beverage`/`alcohol` 跨 cohort 返回 `400`,有效 15 个),乘上分页与搜索,缓存键是发散的。这带来三个具体代价:

1. **运维**:任何一次数据变更都要 purge 全部键 + 逐键预热。这套动作已经出过错——曾经在打标签之前刷缓存,把「缺新品的榜」缓存了下来;而 `/rankings` 的 `Cache-Control` 是 `max-age=86400`,错一次的代价上限是一天。
2. **交互**:品类之间切换、翻页、搜索,每一下都是一次跨境往返(经备案域实测基线 ~1.8s)。
3. **一致性**:15 个键各自独立过期,用户在不同品类间看到的可能是不同时刻的快照。

而榜单**全量只有 389 行**。整张榜一次性下发约 110KB 原始 / 约 25KB gzip,在端上排序、分页、过滤、搜索,可以把这 15+ 个缓存键**塌缩成 1 个**,并让品类切换与翻页变成零网络的本地操作。

排序本身也不该在服务端:排序键就是 `per100ml`,一个已经落库的数值。服务端为此做的闭包 join + `ORDER BY` + 分页,客户端拿到全量后用一次 sort 就能等价复现,且结果**逐字相同**(同一个数值集、同一个升序)。

## What Changes

- **新增全量快照端点**:一次返回当前榜单的**全部**可比行(不分页),作为**单一**可缓存对象。每行在既有 `RankingsItem` 字段基础上**增加所属叶品类 slug** —— 这是客户端本地按品类过滤的必要信息,当前响应里没有。
- **`packages/api-client` 提供本地榜单能力**:消费快照并在端上完成排序、按品类过滤(沿 `/categories` 的 `parentSlug` 判定祖先归属)、分页、按商品名子串搜索。跨 cohort 的拒绝依据 `/categories` 已有的 `comparableUnit === null`,**不需要**新的服务端往返。
- **小程序改为消费快照**:榜单 Tab、分类树下钻、搜索、分页统一从**一份**本地快照派生;端上 SWR 缓存从「每 cohort 一份」改为「一份快照」。
- **`GET /rankings` 保持不变**:它仍是公开只读 API,服务其它客户端(web / 插件)与深链;本变更**不删、不改**其契约。

## Capabilities

### New Capabilities

- `board-snapshot`: 全量榜单快照端点 —— 一次性返回全部可比行(含叶品类 slug)、单一缓存对象、只读、治理豁免口径与 `/rankings` 一致。

### Modified Capabilities

- `api-client`: 新增快照 schema / 解析函数,以及本地排序 / 过滤 / 分页 / 搜索能力;跨 cohort 判定依据从「服务端 `400`」改为「本地据 `comparableUnit`」。
- `miniapp`: 榜单骨架、分页三态、搜索、分类树下钻、SWR 缓存**五条需求**的数据来源统一改为本地快照;端上**允许**排序(既有需求明文「禁止端上重排」需相应修正)。

## 非目标

- **不做**端上单价计算。榜单展示的 `per100ml` 仍是**服务端已落库的存储值**,端上**只排序、不重算** —— 这条与 `rankings-api` 既有的「读路径禁止重算 `per100ml`」一致,不动摇。
- **不删、不改** `GET /rankings` 的请求/响应契约。
- **不动**入库、打标签、cohort 规则表的归属(`resolveComparableUnitStatic` 仍在服务端)。
- **不做**榜单以外的本地化(即时比价的算术是另一个提案)。
- **不解决**规模上限问题:本设计在**当前量级**(百量级行)成立,失效阈值与降级路径见 design,但**本期不实现**降级。
- **不碰**抓取/众包合规面。

## Impact

- **workspace 包**:`apps/api`(新增端点 + 投影加一列)、`packages/api-client`(新 schema + 本地榜单能力)、`apps/miniapp`(五条需求的数据来源)。`packages/core` **零改动**、`packages/db` 仅新增一个全量查询。
- **API**:**新增**一个只读端点;既有端点**零变更**。
- **缓存**:榜单相关的 CDN 缓存键由 15+ 收敛为 1,purge/预热流程随之简化(`docs/backfill-runbook.md` 的 CDN 一节需同步)。
- **合规**:只读、不抓取、不新增出站、不触 LLM。**不涉及**合规敏感面。
- **规模**:当前 389 行 ≈ 110KB 原始 / ~25KB gzip。该数字随目录增长线性上升,**这是本设计的主要风险**,见 design 的失效阈值。
- **变更体量**:本变更明显重于同批的 `client-side-compute` —— 它新增一个端点、改一个共享 schema、并触及 `miniapp` 的五条需求。若要压缩单次风险,可先只落「快照端点 + api-client 能力」、再单独立项切换 miniapp;但那样中间态没有用户可见价值。本提案按**一次做完**组织。
