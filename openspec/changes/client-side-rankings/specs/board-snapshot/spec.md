## 新增需求

### 需求:必须提供全量榜单快照端点作为单一可缓存对象

`apps/api` **必须**提供一个**只读**端点,一次返回当前榜单的**全部**可比行(`per100ml` 非空且 `rankable`),**不分页、不接受品类 / 搜索 / 分页参数**。它的存在理由就是「只有一个缓存键」——任何会使响应随参数分叉的设计都违背本需求。

**投影**:每行的字段集**必须**与 `/rankings` 的行**同源**(共用同一段投影逻辑,**禁止**各写一份导致同一行在两个端点字段不一致),并在其上**增加所属叶品类 slug**。该 slug 是客户端本地按品类过滤的必要信息;祖先归属由客户端沿 `/categories` 的 `parentSlug` 自行推导,故**禁止**下发闭包表或完整路径字符串(冗余,且路径格式会成为新的隐式契约)。

**`rank` 不在快照行内**:`rank` 是「某个过滤 + 排序视图下的读时位次」,在全量无序集合里没有定义。由客户端在排序后赋值,语义与 `/rankings` 的 `rank = offset + 1-based index` 一致。

**排序稳定性**:客户端与服务端对同一数值集排序必须得到相同序列。故 `per100ml` **相等**时的次序**必须**由一个确定性 tie-breaker 决定(而非依赖实现的排序稳定性),且该口径**必须**与 `/rankings` 的一致——否则同一份数据在小程序与 web 上顺序不同。

**只读与治理**:与 `/rankings` 同口径——只读、不重算、不写库、治理豁免(不消耗公共限频、不记 usage)。响应**必须**可被 CDN 缓存。

**规模可观测**:响应**必须**使当前行数可被观测(响应内或日志),使「快照大到不该再整发」这件事有据可依,而不是等首屏变慢才发现。

`GET /rankings` **不受本需求影响**:其请求 / 响应契约**保持不变**,继续服务其它客户端与深链,并作为快照方案在规模超限后的回退路径。

#### 场景:一次返回全部可比行且不接受过滤参数

- **当** 客户端请求快照端点
- **那么** **必须**返回当前**全部** `per100ml` 非空且 `rankable` 的行(不分页);**禁止**接受品类 / 搜索 / 分页参数使响应分叉成多个缓存对象

#### 场景:每行携带叶品类 slug

- **当** 快照返回任意一行
- **那么** 该行**必须**携带其所属**叶**品类 slug;**禁止**下发祖先闭包或路径字符串(客户端已有 `/categories` 全树,据 `parentSlug` 自行推导祖先归属)

#### 场景:快照行与 /rankings 行字段同源

- **当** 同一个商品同时出现在快照与 `GET /rankings` 的响应中
- **那么** 二者共有字段的值**必须**逐字相同;实现**必须**共用同一段投影逻辑,**禁止**复制出两份

#### 场景:per100ml 相等时次序确定

- **当** 两行的 `per100ml` 完全相等
- **那么** 二者的先后**必须**由确定性 tie-breaker 决定、结果可复现,且与 `/rankings` 的排序口径一致;**禁止**依赖底层排序实现是否稳定

#### 场景:只读且不改变任何存储值

- **当** 快照端点被调用任意次
- **那么** **禁止**发生任何写入,**禁止**重算 `per100ml`(它是存储值);端点**必须**可被 CDN 缓存
