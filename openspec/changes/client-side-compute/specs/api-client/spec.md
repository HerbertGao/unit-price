## 新增需求

### 需求:api-client 必须提供与 /compute 同源的本地单价计算

`packages/api-client` **必须**导出一个**本地**单价计算函数,接受与 `ComputeRequest` **相同**的结构化输入(`totalPrice` + `unitSize`/`quantity` 或 `totalAmount`,单位 `ml`/`L`/`g`/`kg`),同步返回单价(`per100ml`/`per100g`)与可回放的 `formula`,**不发起任何网络请求**。

**同源是硬约束**:该函数**必须**调用 `packages/core` 的 `calculate()`(经其 Zod-free 算术子入口),**禁止**在本包内重写或复制任何单位换算、一致性校验或单价公式——两份实现漂移的后果是「同一件商品算出不同的钱」。输入到 `ParsedSpec` 的映射**必须**与 `apps/api` 的 `/compute` 处理器逐字同构(含「输入集是否足够」的判定与不可计算时的处理),使同一输入在两侧产出**逐字相同**的单价与 `formula`。

**依赖边界**:本包**允许**依赖 core 的**算术子入口**;**禁止**从 core 根入口 import,亦**禁止**依赖 core 中任何带 Zod 的模块(`types` / `category-rules`)——本包被打进微信小程序,而那两个坑(现代语法转译破坏 Zod class、Zod JIT `new Function` 撞 eval 禁用)正是由 Zod 引入的。既有「`/compute` 客户端模块自包含」的架构测试**必须**收窄为这一边界断言、**禁止**直接删除:它保护的风险是真实的,只是原先边界画得过粗。

**`POST /compute` 端点及其请求/响应契约不变**:该端点仍是 cohort 内定位(`rank`/`total`/`percentile`/`neighbors`)的唯一来源——那部分**必须**读库、无法本地化。本需求只让**算术**不再依赖网络。

#### 场景:本地计算与 /compute 对同一输入产出相同结果

- **当** 用同一组结构化输入分别调用本地计算函数与 `POST /compute`
- **那么** 二者的单价(`per100ml`/`per100g`)与 `formula` 字符串**必须**逐字相同;本变更**必须**留一组对照测试守住该等价性

#### 场景:本地计算不发起网络请求

- **当** 调用本地计算函数
- **那么** **禁止**发起任何网络请求;函数**必须**同步返回,在设备离线时同样可用

#### 场景:输入集不足或不可计算时不产出数字

- **当** 输入集不足(既无总量、也无「单件容量 + 数量」)或计算结果不可算(如总价 ≤ 0)
- **那么** **必须**返回明确的不可计算态并携带原因,**禁止**返回 `0`、`null` 或任何会被渲染成单价的数字;判定口径**必须**与 `/compute` 的对应 `400` 一致

#### 场景:禁止从 core 根入口或带 Zod 的模块 import

- **当** 检查本包的模块依赖
- **那么** **禁止**出现对 `@unit-price/core` 根入口的 import,**禁止**出现对 core 中带 Zod 模块的 import;架构测试**必须**断言这一点,**禁止**因放宽而删除该测试

#### 场景:cohort 合法性仍由服务端裁决

- **当** 用户选了一个跨多个可比口径的品类(无静态可比单位)
- **那么** 本地计算**不承担**该判定;跨 cohort 的拒绝仍由 `/compute` 以 `400` 给出,客户端按既有契约呈现其 `message`
